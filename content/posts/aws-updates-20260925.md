# 今回は、直近で発表された12件のAWSアップデートを紹介します

AWS では様々なサービスの機能拡張やリージョン拡大が継続的に行われています。今回取り上げる12件のアップデートでは、データベースサービスの機能強化、グローバル展開の加速、そしてセキュリティ機能の拡充が目立ちます。特に注目すべきは、RDS for PostgreSQL における耐量子暗号対応、DynamoDB グローバルテーブルのマルチリージョン強い一貫性機能の拡大、そして Kinesis Data Streams のサービスマネージド パーティションキー機能です。これらは運用の簡素化とセキュリティ強化を同時に実現する重要なアップデートとなっています。

本記事では、これらのアップデートの中から特に影響範囲が大きいものをピックアップし、技術的な深掘りと SRE 視点での活用ポイントを解説します。

## 注目アップデート深掘り

### Amazon RDS for PostgreSQL の耐量子暗号（PQ-TLS）対応

Amazon RDS for PostgreSQL が PostgreSQL 18 以上で耐量子暗号（Post-Quantum Cryptography）に対応した TLS キー交換をサポートしました。量子コンピュータの実用化が進む中、現在の公開鍵暗号方式は将来的に解読される可能性があり、長期的なデータ保護の観点から先制的な対策が求められています。

#### なぜ今、耐量子暗号なのか

従来の RSA や楕円曲線暗号（ECC）といった公開鍵暗号方式は、現代のコンピュータでは解読が困難ですが、量子コンピュータが実用化されると短時間で解読される可能性があります。特に「Store Now, Decrypt Later（今記録して後で解読）」と呼ばれる脅威モデルでは、攻撃者が現在暗号化された通信を記録しておき、将来量子コンピュータで解読することが想定されています。金融機関や医療機関など、長期的なデータの機密性が求められる組織では、今から対策を講じる必要があります。

#### 設定方法と技術的背景

PostgreSQL 18 では、`ssl_groups` パラメータを使用して、TLS 接続で使用する暗号グループを制御できます。RDS Management Console または AWS CLI を通じて、このパラメータを変更することで、許可リストから量子耐性のある暗号グループを選択できます。

設定の変更は、データベースパラメータグループを通じて行います。既存の PostgreSQL インスタンスを PostgreSQL 18 にアップグレードした後、パラメータグループで `ssl_groups` を更新し、インスタンスを再起動することで有効化されます。この設定により、クライアントとデータベース間の TLS ハンドシェイク時に、NIST が標準化した耐量子暗号アルゴリズム（ML-KEM など）を使用したキー交換が可能になります。

#### 従来の TLS との違い

従来の TLS 1.2/1.3 では、鍵交換に ECDHE（Elliptic Curve Diffie-Hellman Ephemeral）などが使用されていました。これらは現在のコンピュータに対しては十分に安全ですが、量子コンピュータの Shor のアルゴリズムによって効率的に解読される可能性があります。

耐量子暗号では、格子暗号や符号ベース暗号など、量子コンピュータでも効率的な解読アルゴリズムが知られていない数学的問題に基づいた暗号方式を使用します。PostgreSQL 18 の実装では、NIST が標準化した ML-KEM（Module-Lattice-Based Key-Encapsulation Mechanism）などのアルゴリズムがサポートされています。

#### パフォーマンスへの影響

耐量子暗号アルゴリズムは、従来の楕円曲線暗号と比較して計算量が増加する傾向があります。TLS ハンドシェイク時の処理時間がわずかに増加する可能性がありますが、一度接続が確立された後のデータ転送には影響しません。高頻度で接続を確立・切断するアプリケーションでは、接続プーリングの活用がより重要になります。

移行を検討する際は、まず RDS Database Preview Environment などで性能検証を行い、アプリケーションの接続パターンにおける影響を測定することが推奨されます。

### Amazon Kinesis Data Streams のサービスマネージド パーティションキー機能

Amazon Kinesis Data Streams に追加されたサービスマネージド パーティションキー機能により、開発者はパーティションキーを明示的に指定せずにデータを送信できるようになりました。この機能は、ストリーミングデータ取り込みの運用を大幅に簡素化し、ホットパーティション問題を根本的に解決します。

#### ホットパーティション問題とは

従来、Kinesis Data Streams にデータを送信する際は、各レコードにパーティションキーを指定する必要がありました。Kinesis はこのパーティションキーをハッシュ化し、その値に基づいてレコードを特定のシャードに割り当てます。しかし、パーティションキーの選択が適切でない場合、特定のシャードにトラフィックが集中する「ホットパーティション」が発生し、スロットリングエラーが頻発する問題がありました。

例えば、ユーザー ID をパーティションキーとして使用する場合、特定の人気ユーザーのデータが特定のシャードに集中し、そのシャードだけが容量上限に達してしまうケースがありました。この問題を回避するため、多くの開発者はランダムな UUID を生成してパーティションキーとして使用していましたが、これには UUID 生成のオーバーヘッドと、コードの複雑化という課題がありました。

#### サービスマネージド パーティションキーの仕組み

新機能では、パーティションキーを省略してレコードを送信すると、AWS が自動的に利用可能な容量に基づいてレコードをシャード全体に均等に分散させます。この分散ロジックは AWS 側で最適化されており、シャードの現在の使用状況をリアルタイムに考慮して配置が決定されます。

この機能は On-Demand Standard および On-Demand Advantage ストリームで利用可能です。On-Demand モードでは容量管理が自動化されているため、サービスマネージド パーティションキーとの組み合わせにより、ストリーミングインフラの運用がほぼ完全に自動化されます。

#### 適用すべきユースケース

この機能が特に効果を発揮するのは、レコードの順序保証が不要なユースケースです。ログ集約システムでは、複数のアプリケーションサーバーから送信されるログの順序は重要ではなく、全体として高スループットで取り込めることが重要です。同様に、IoT デバイスから送信されるテレメトリデータ、リアルタイム監視メトリクス、アクセスログの中央集約などが該当します。

一方で、金融取引の履歴や注文処理など、特定のエンティティに対する操作の順序を保証する必要がある場合は、引き続き明示的なパーティションキー（例：ユーザー ID、注文 ID）を指定する必要があります。Kinesis は同一パーティションキーを持つレコードを同一シャードに配置し、その順序を保証するため、順序性が重要なワークロードでは従来の方式を継続します。

#### 移行とベストプラクティス

既存のストリーミングアプリケーションからの移行は、最新の AWS SDK または Kinesis Producer Library (KPL) にアップグレードすることで可能になります。コード上では、パーティションキーの指定を単純に省略するだけで、自動分散が有効化されます。

段階的な移行を行う場合は、まず新規ストリームで検証を行い、CloudWatch メトリクスで各シャードへのレコード分散状況を監視します。`IncomingRecords` や `IncomingBytes` メトリクスをシャード別に確認することで、分散が適切に行われているかを確認できます。その後、既存のストリームを段階的に移行することで、リスクを最小化できます。

### DynamoDB グローバルテーブルのマルチリージョン強い一貫性（MRSC）機能の拡大

Amazon DynamoDB のグローバルテーブルにおけるマルチリージョン強い一貫性（MRSC）機能が、5つの新リージョンに対応し、合計15リージョンで利用可能になりました。これにより、北米、ヨーロッパ、アジアパシフィックの3大陸にまたがる構成が可能になり、真のグローバルアプリケーションの構築が現実的になりました。

#### なぜマルチリージョン強い一貫性が重要なのか

従来の DynamoDB グローバルテーブルは、結果整合性（Eventual Consistency）モデルを採用していました。これは、あるリージョンでの書き込みが他のリージョンに反映されるまでに数秒程度の遅延が発生することを意味します。多くのユースケースではこれで問題ありませんが、在庫管理、金融取引、権利管理など、データの一貫性が即座に必要なアプリケーションでは課題となっていました。

MRSC 機能は、複数リージョン間で強い一貫性を保証します。これにより、あるリージョンで書き込みが成功した時点で、他の参加リージョンからも最新の値が即座に読み取れることが保証されます。さらに、RPO（目標復旧時点）がゼロとなるため、リージョン障害が発生しても、他のリージョンには障害発生直前までのすべてのデータが存在することが保証されます。

#### 構成オプション：3レプリカ vs 2レプリカ + ウィットネス

MRSC グローバルテーブルは、3つのリージョンを使用して構成されます。このとき、2つの構成パターンから選択できます。

**3レプリカ構成**では、3つのリージョンすべてでデータの完全なコピーを保持します。すべてのリージョンで読み取り・書き込みが可能で、ユーザーに最も近いリージョンにルーティングすることで低レイテンシーを実現できます。この構成は、3つのリージョンすべてでアプリケーションが活発に稼働しているグローバルサービスに適しています。

**2レプリカ + ウィットネスリージョン構成**では、2つのリージョンでデータの完全なコピーを保持し、3つ目のリージョンはウィットネス（監視役）として機能します。ウィットネスリージョンはデータのコピーを持たず、合意形成（コンセンサス）のための投票にのみ参加します。この構成は、主要な2つのリージョンでトラフィックがあり、3つ目のリージョンは障害対策のためだけに使用する場合に、ストレージコストを削減できます。

#### クロスコンティネント構成の可能性

今回の拡張により、北米（例：米国東部）、ヨーロッパ（例：スペイン）、アジアパシフィック（例：シンガポール）にまたがる3リージョン構成が可能になりました。これは、真のグローバルサービスにとって重要な進化です。

例えば、グローバルな e-コマースプラットフォームでは、在庫情報を3大陸で共有し、どのリージョンで注文が発生しても、他のリージョンの在庫状況を即座に反映できます。これにより、オーバーセル（在庫を超える販売）を防ぎながら、各地域のユーザーに低レイテンシーでサービスを提供できます。

地理的に分散した構成は、大規模災害や地政学的リスクに対する耐性も向上させます。1つの大陸全体が影響を受けるような事態でも、他の2大陸でサービスを継続できる設計が可能になります。

## SRE視点での活用ポイント

### 耐量子暗号対応の導入判断

RDS for PostgreSQL の耐量子暗号対応は、今すぐすべての環境で必須というわけではありませんが、長期的なセキュリティ戦略として検討する価値があります。特に、金融情報、医療データ、個人識別情報など、長期的な保護が求められるデータを扱うシステムでは、早期の検証と段階的な導入計画を立てることが推奨されます。

導入にあたっては、まず非本番環境で PostgreSQL 18 へのアップグレードと `ssl_groups` パラメータの設定を検証します。特に注意すべきは、アプリケーション側の PostgreSQL クライアントライブラリが耐量子暗号に対応しているかの確認です。古いクライアントライブラリでは、サーバー側で耐量子暗号を有効化しても接続に失敗する可能性があります。

CloudWatch メトリクスで接続確立時間（connection time）を監視し、耐量子暗号導入前後での変化を測定することで、パフォーマンスへの影響を定量的に把握できます。接続プール（PgBouncer、RDS Proxy など）を使用している環境では、接続の再利用により TLS ハンドシェイクの頻度が低いため、影響はさらに小さくなります。

### Kinesis のサービスマネージド パーティションキーでの運用簡素化

ログ集約やメトリクス収集のパイプラインでは、Kinesis のサービスマネージド パーティションキー機能により、コードの複雑さと運用負荷を大幅に削減できます。従来、ホットパーティション問題を回避するために UUID 生成ロジックやハッシュ関数を実装していた部分を、単純にパーティションキーを省略するだけで置き換えられます。

移行時は、既存のストリームに対してまずカナリアデプロイメントを実施し、一部のプロデューサーからのみ新方式でデータを送信して動作を確認します。CloudWatch のカスタムメトリクスで、シャードごとの `IncomingRecords` を監視し、分散が均等に行われているかを確認します。不均等な分散が観測された場合は、AWS サポートと連携して原因を特定します。

アラーム設定では、個別シャードの `WriteProvisionedThroughputExceeded` メトリクスに加えて、ストリーム全体のスロットリング率を監視することで、ホットパーティション問題の早期検出が可能です。On-Demand モードを使用している場合、容量は自動的にスケールしますが、急激なトラフィック増加時には短時間のスロットリングが発生する可能性があるため、リトライロジックの実装は引き続き重要です。

### DynamoDB MRSC でのグローバル展開設計

DynamoDB のマルチリージョン強い一貫性機能を活用する際は、レイテンシーとコストのトレードオフを慎重に検討する必要があります。MRSC は、書き込み時に複数リージョン間でコンセンサスを取る必要があるため、単一リージョンや結果整合性のグローバルテーブルと比較して、書き込みレイテンシーが増加します。

リージョン選定では、主要なユーザーベースが存在する地域と、災害復旧要件を考慮します。3大陸にまたがる構成を採用する場合、各リージョン間のネットワークレイテンシーが全体の応答時間に影響するため、AWS のリージョン間レイテンシーを事前に測定しておくことが重要です。

Terraform や CloudFormation でインフラを管理している場合、MRSC グローバルテーブルの定義では各レプリカリージョンと構成タイプ（レプリカかウィットネスか）を明示的に指定します。リージョン障害時のフェイルオーバー手順をランブックに記載し、Route 53 の health check と組み合わせた自動フェイルオーバーを構成することで、RPO ゼロ・RTO 最小化の高可用性アーキテクチャを実現できます。

コスト管理の観点では、ウィットネスリージョンの活用により、3つ目のリージョンでのストレージコストを削減できます。一方、2つのアクティブリージョンでのトラフィックが十分に高い場合、3レプリカ構成により各リージョンでの読み取りレイテンシーを最小化できるため、ユーザー体験とコストのバランスを考慮して選択します。

## まとめ

今回紹介したアップデートは、AWS のサービスがより使いやすく、より安全に、そしてよりグローバルに展開できる方向に進化していることを示しています。

特に注目すべきトレンドとして、**運用の自動化と簡素化**が挙げられます。Kinesis のサービスマネージド パーティションキーや、Network Security Manager による一元管理機能は、従来手作業で行っていた複雑な設定や調整を AWS に委任できるようになりました。これにより、エンジニアはビジネスロジックにより多くの時間を割くことができます。

**セキュリティの先制的強化**も重要なテーマです。RDS for PostgreSQL の耐量子暗号対応は、量子コンピュータの実用化という将来の脅威に対して、今から備えることができる機能です。長期的なデータ保護が求められる組織にとって、セキュリティ戦略の重要な選択肢となるでしょう。

**グローバル展開の容易化**では、GameLift のリージョン拡大、DynamoDB MRSC の拡張、EMR on EKS の IPv6 対応など、世界中のユーザーに低レイテンシーでサービスを提供するための基盤が着実に整備されています。特に DynamoDB の MRSC がクロスコンティネント構成に対応したことで、真のグローバルアプリケーションの構築が現実的になりました。

データベースとアナリティクス領域では、PostgreSQL 19 Beta の早期アクセス、MySQL の拡張サポート、EMR on EKS の Spark Connect 対応など、開発者体験の向上と長期的な運用サポートの両面が強化されています。これらのアップデートを活用することで、よりモダンで保守性の高いデータプラットフォームを構築できます。
