# New Relic アップデート情報（2026/09/17）

## はじめに

2026年9月17日、New Relic から Infrastructure Agent の新バージョン 1.80.4 がリリースされました。今回のアップデートは単一のコンポーネントに焦点を当てたものですが、その内容は多岐にわたります。依存ライブラリの大幅な更新、systemd互換性の重要な改善、セキュリティパッチの適用、そして運用安定性を高める機能追加が含まれています。

特に注目すべきは、systemd 231以降で非推奨となった `MemoryLimit` 設定への対応です。これは多くのLinux環境で稼働するInfrastructure Agentに影響を与える変更であり、メモリ制限の設定方法を見直す必要があります。また、nrjmx、nri-prometheus、nri-flexといった主要な統合モジュールのアップデートにより、JMX監視、Prometheusメトリクス収集、カスタムメトリクス取得の各機能が強化されています。さらに、gRPCとcontainerdの脆弱性対応により、セキュリティ基盤も強化されました。

## 注目アップデート深掘り

### systemd互換性の改善：MemoryLimit非推奨化への対応

今回のアップデートで最も重要な変更の一つが、systemd 231以降における `MemoryLimit` の非推奨化への対応です。systemdはLinuxシステムの初期化システムとして広く使われており、サービスのリソース制限を管理する重要な役割を担っています。

**なぜこのアップデートが重要なのか**

systemd 231以降では、`MemoryLimit` パラメータが非推奨となり、代わりに `MemoryMax` の使用が推奨されています。古い設定のままではメモリ制限が正しく機能しなくなる可能性があり、Infrastructure Agentが想定以上のメモリを消費してホストシステムに悪影響を与えるリスクがあります。特にコンテナ環境やマイクロサービスアーキテクチャでは、複数のエージェントやアプリケーションが同一ホスト上で動作するため、一つのプロセスのメモリ暴走がシステム全体の安定性を脅かす可能性があります。

**SREの日常業務への具体的な影響**

Infrastructure Agentのメモリ制限が適切に機能しないと、監視システム自体がモニタリング対象システムのパフォーマンスを低下させる本末転倒な状況が発生します。特に、高負荷時や異常なメトリクススパイクが発生した際に、エージェントが過剰なメモリを消費してアラートの遅延や欠損を引き起こす可能性があります。今回の対応により、systemdの最新仕様に準拠した適切なリソース管理が可能となり、監視システムの信頼性が向上します。

現在systemd 231以降の環境で Infrastructure Agent を運用している場合は、systemdのサービス定義ファイルを確認し、`MemoryMax` への移行を検討する必要があります。これにより、エージェントのメモリ使用量が適切に制限され、ホストシステムの安定性が保たれます。

### 依存ライブラリの包括的アップデート

今回のリリースでは、nrjmx v2.14.0、nri-prometheus v2.30.4、nri-flex v1.18.13という3つの主要な統合モジュールが更新されました。これらは Infrastructure Agent の機能を拡張し、特定の監視対象からメトリクスを収集する役割を担っています。

**なぜこのアップデートが重要なのか**

nrjmxはJavaアプリケーションのJMXメトリクスを収集し、nri-prometheusはPrometheus形式のメトリクスをNew Relicに取り込み、nri-flexはカスタムスクリプトやAPIから柔軟にメトリクスを取得します。これらの統合モジュールは、多様なアプリケーションやインフラストラクチャコンポーネントを統一的に監視するための基盤です。各モジュールのアップデートにより、メトリクス収集の精度向上、パフォーマンス改善、新しいデータソースへの対応が実現されます。

**SREの日常業務への具体的な影響**

JMXを利用したJavaアプリケーション監視では、ガベージコレクションやスレッドプール、コネクションプールなどの重要なメトリクスを収集しています。nrjmxのアップデートにより、これらのメトリクスの収集がより安定し、既存のダッシュボードやアラート設定がより正確なデータに基づいて動作するようになります。

Prometheus統合を使用している環境では、Kubernetesクラスターやコンテナ化されたアプリケーションからのメトリクス収集が改善されます。nri-prometheusの更新により、スクレイピングの効率が向上し、大規模なクラスター環境でもメトリクスの取得遅延が軽減される可能性があります。

nri-flexは、独自のAPIやカスタムスクリプトからメトリクスを取得する際に活用されます。このモジュールの更新により、特殊な監視要件に対応する柔軟性がさらに向上します。

### セキュリティパッチの適用

gRPCとcontainerdのセキュリティパッチが含まれている点も見逃せません。gRPCはInfrastructure AgentがNew Relicのバックエンドと通信する際に使用されるプロトコルであり、containerdはコンテナランタイムとして広く利用されています。

**なぜこのアップデートが重要なのか**

セキュリティ脆弱性は、監視システムそのものが攻撃の入り口となるリスクをはらんでいます。Infrastructure Agentは通常、ホストシステムの広範な情報にアクセスする権限を持っており、脆弱性が悪用されると、監視対象システム全体のセキュリティが危険にさらされます。今回のパッチ適用により、既知の脆弱性が解消され、本番環境の安全性が向上します。

**SREの日常業務への具体的な影響**

セキュリティインシデントの発生は、SREにとって最も避けたい事態の一つです。パッチが適用されていないエージェントは、セキュリティスキャンで脆弱性として検出され、コンプライアンスチェックに引っかかる可能性があります。今回のアップデートにより、セキュリティチームからの指摘や監査対応の手間が軽減されます。

特にコンテナ環境では、containerdの脆弱性がコンテナエスケープなどの深刻な問題につながる可能性があります。早期に最新バージョンへアップグレードすることで、こうしたリスクを未然に防ぐことができます。

### 運用安定性の向上：一時ファイル所有権チェック

今回のアップデートでは、一時ファイルの所有権チェックが追加されました。これは地味ながら重要な改善です。

**なぜこのアップデートが重要なのか**

Infrastructure Agentは動作中に一時ファイルを作成し、メトリクスの一時保存や統合モジュールとのデータ交換に利用します。ファイルシステムの権限問題により、これらの一時ファイルへのアクセスが失敗すると、メトリクス収集の欠損やエージェントの異常終了につながります。所有権チェックの追加により、権限問題を早期に検出し、適切なエラーメッセージを出力できるようになります。

**SREの日常業務への具体的な影響**

これまで、ファイルシステム関連の問題はトラブルシューティングが困難なケースが多くありました。エージェントが突然メトリクスを送信しなくなったり、統合モジュールが動作しなくなったりした際、原因がファイルの権限問題であることを特定するまでに時間がかかることがありました。今回の改善により、ログに明確なエラーメッセージが出力されるようになり、問題の切り分けと解決が迅速化されます。

特にコンテナ環境やセキュリティが厳密に管理された環境では、ファイルシステムの権限設定が複雑になりがちです。所有権チェック機能により、デプロイ時やコンテナイメージ更新時に権限問題を早期発見できるようになります。

## SRE視点での活用ポイント

### 監視・アラート・ダッシュボードへの影響

今回のアップデートは、直接的に新機能を追加するものではありませんが、既存の監視体制の信頼性と精度を向上させます。依存ライブラリの更新により、JMXメトリクス、Prometheusメトリクス、カスタムメトリクスの収集精度が向上するため、既存のダッシュボードがより正確なデータを表示するようになります。アラート設定についても、メトリクスの欠損や遅延が減少することで、誤検知や検知漏れのリスクが低下します。

特に、systemd互換性の改善により、エージェント自体のリソース管理が適切になることで、高負荷時でも安定したメトリクス収集が期待できます。これは、障害発生時に「監視システムが正常に動作しているか」という不安を軽減し、インシデント対応に集中できる環境を提供します。

### AWS環境でのNew Relicエージェント運用における影響

EC2インスタンスでInfrastructure Agentを運用している場合、Amazon Linux 2やUbuntu、Red Hat Enterprise Linuxなど、systemd 231以降を使用するディストリビューションでは、今回のアップデートが特に重要です。Auto Scaling環境では、起動テンプレートやユーザーデータスクリプトでエージェントをインストールする際に、最新バージョンを指定することで、systemd互換性の問題を回避できます。

ECS（Elastic Container Service）やEKS（Elastic Kubernetes Service）でコンテナ化されたアプリケーションを運用している場合、containerdのセキュリティパッチが特に重要です。コンテナイメージにInfrastructure Agentをサイドカーとして組み込んでいる場合は、ベースイメージの更新を検討してください。

Lambda環境では直接Infrastructure Agentを使用しませんが、Lambda関数からカスタムメトリクスを送信する際に、同じバックエンドAPIを利用しているため、gRPCのセキュリティ改善は間接的に影響します。

### すぐに試せるTips

まず、現在のInfrastructure Agentのバージョンを確認してください。多くのLinuxディストリビューションでは、エージェントのバージョン情報はログファイルや `/etc/newrelic-infra/` ディレクトリの設定ファイルで確認できます。

次に、systemdのバージョンを確認し、231以降であれば、サービス定義ファイルで `MemoryLimit` が使用されていないか確認してください。使用されている場合は、`MemoryMax` への移行を計画します。

アップグレード前に、テスト環境で動作確認を行うことを推奨します。特に、JMX統合、Prometheus統合、Flex統合を使用している場合は、メトリクスが正しく収集されることを確認してください。

### アップグレード時の注意点やリスク

Infrastructure Agentのアップグレードは通常、比較的安全な作業ですが、本番環境での一斉アップグレードは避け、段階的なロールアウトを推奨します。まず、非クリティカルな環境やカナリアインスタンスでアップグレードを実施し、数時間から数日間の安定稼働を確認してから、本番環境全体に展開します。

systemd設定の変更を伴う場合は、サービスの再起動が必要になる可能性があるため、メンテナンスウィンドウを設定することを推奨します。特に、メモリ制限の設定を変更する場合は、エージェントの動作に影響を与える可能性があるため、慎重に実施してください。

依存ライブラリのアップデートにより、統合モジュールの動作が変わる可能性があります。特に、カスタムダッシュボードやアラート設定で特定のメトリクス名や属性名に依存している場合は、アップグレード後に動作確認を行ってください。

セキュリティパッチが含まれているため、早期のアップグレードが望ましいですが、変更管理プロセスに従い、適切な承認と記録を残すことを忘れないでください。

## まとめ

今回のInfrastructure Agent 1.80.4のリリースは、新機能の追加ではなく、既存機能の品質向上とセキュリティ強化に焦点を当てたアップデートです。しかし、その内容は決して地味ではありません。systemd互換性の改善は、多くのLinux環境で稼働するエージェントの長期的な安定性を確保するための重要な対応であり、依存ライブラリの更新はメトリクス収集の信頼性を高めます。セキュリティパッチの適用は、監視システム自体がセキュリティリスクとならないための必須対応です。

SREの視点では、「監視システムの監視」という難しい課題に取り組む上で、このような基盤的な改善は極めて重要です。派手な新機能よりも、日々の運用を支える安定性と信頼性こそが、真に価値のある改善と言えるでしょう。

特にコンテナ環境、JMX監視、Prometheus統合を活用している場合は、今回のアップデートから得られるメリットが大きいため、計画的なアップグレードを検討することを推奨します。セキュリティパッチが含まれていることも考慮し、リスク評価に基づいて適切なタイミングでのアップグレードを実施してください。
