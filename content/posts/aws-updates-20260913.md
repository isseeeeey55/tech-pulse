# 直近の AWS アップデートまとめ

## はじめに

今回は、直近で発表された AWS Lambda に関する 1 件のアップデートを紹介します。AWS Lambda が Amazon S3 Files からのダイレクト読み込み設定をサポートし、メモリサイズに関係なく読み込み元ストレージを明示的に制御できるようになりました。このアップデートは、Lambda 関数のパフォーマンス特性を細かくチューニングしたい場面で有用です。

## 注目アップデート深掘り

### AWS Lambda が Amazon S3 Files のダイレクト読み込み設定に対応

#### なぜこのアップデートが重要なのか

従来、Lambda 関数が S3 Files（Lambda のマウント可能なストレージオプション）を利用する際、メモリが 512 MB 以上の関数に限り S3 バケットから直接読み込む動作が行われていました。しかし、この動作は自動的に決定されるため、アプリケーションの特性に応じた最適化が困難でした。特に、小さなファイルを多数扱う AI エージェントやリアルタイム推論ワークロードでは、最小レイテンシーが求められる一方、大規模なデータ分析パイプラインではスループットを最大化したいというトレードオフが存在します。

今回のアップデートにより、メモリサイズに関係なく、ダイレクト読み込みの有効・無効を明示的に制御できるようになりました。これにより、アプリケーションの要件に応じて、レイテンシー優先かスループット優先かを開発者が選択できるようになります。

#### 動作の仕組みとビフォーアフター

**従来の動作：**

- メモリ 512 MB 以上：自動的に S3 バケットからのダイレクト読み込みが有効
- メモリ 512 MB 未満：すべて高性能ストレージから提供

**新しい動作（ダイレクト読み込み有効時）：**

- 1 MB 以上のファイル：S3 バケットから直接読み込み（スループット最大化）
- 1 MB 未満のファイル：高性能ストレージから提供（レイテンシー最小化）

**新しい動作（ダイレクト読み込み無効時）：**

- すべてのファイル：高性能ストレージから提供（最小レイテンシー）

この設定により、例えば 128 MB のメモリで動作する関数でも、大きなファイルを扱う際にはダイレクト読み込みを有効にしてスループットを確保できます。逆に、512 MB 以上のメモリを使う関数でも、小さなファイルを多数扱う場合はダイレクト読み込みを無効にして、すべてのファイルを高性能ストレージから取得することで、一貫して低レイテンシーを実現できます。

#### 設定方法

リリースノートによれば、AWS Management Console、CLI、SDK、CloudFormation から設定可能とされています。具体的なパラメータ名やコマンド体系は告知に記載されていないため、詳細は公式ドキュメントを参照してください。設定は追加料金なしで利用でき、標準の Lambda と S3 Files の料金のみが適用されます。

#### 検証のポイント

このアップデートを評価する際は、以下のような比較検証が推奨されます。

**1. ファイルサイズごとのパフォーマンス測定**

100 KB、1 MB、10 MB、100 MB といった異なるサイズのファイルを用意し、ダイレクト読み込みの ON/OFF でレイテンシーとスループットを測定します。特に 1 MB の境界で動作が切り替わるため、その前後でのパフォーマンス特性の変化を確認することが重要です。

**2. メモリサイズの影響確認**

従来の動作では 512 MB が境界となっていましたが、新しい設定ではこの制約がなくなっています。128 MB、256 MB、512 MB、1024 MB といった異なるメモリサイズで、設定が期待通りに機能することを検証します。

**3. 混合ワークロードでの挙動**

同一関数内で小さなファイルと大きなファイルの両方を扱う場合、ダイレクト読み込み有効時には自動的に最適な読み込み元が選択されるはずです。実際のアプリケーションに近いワークロードで、この動作が適切に機能するか確認します。

## SRE 視点での活用ポイント

このアップデートは、Lambda を使ったデータ処理パイプラインや AI/ML ワークロードの運用において、パフォーマンスとコストのバランスを細かく調整できる選択肢を提供します。

**レイテンシーが重要なユースケース**では、ダイレクト読み込みを無効にすることで、すべてのファイルアクセスを高性能ストレージ経由にし、一貫して低レイテンシーを確保できます。例えば、リアルタイム推論 API や、ユーザーリクエストに応じて設定ファイルを読み込む同期処理では、数ミリ秒のレイテンシー改善が体感品質に直結します。

**スループットが重要なバッチ処理**では、ダイレクト読み込みを有効にすることで、大きなファイルを効率的に処理できます。データ分析パイプラインや、数 GB のログファイルを処理する ETL ジョブでは、S3 バケットから直接読み込むことで、高性能ストレージへの負荷を軽減しつつ、スループットを最大化できます。

**導入時の判断基準**としては、まず現在の Lambda 関数がどのようなファイルサイズを扱っているかを確認します。CloudWatch Logs Insights などで S3 Files へのアクセスパターンを分析し、1 MB の境界を意識してワークロードを分類します。小さなファイルが多い場合はダイレクト読み込み無効、大きなファイルが主体の場合は有効が基本戦略となります。

**注意点**としては、設定変更が関数のパフォーマンス特性に影響を与えるため、本番環境に適用する前に、負荷テストやカナリアデプロイでの検証が推奨されます。また、ファイルサイズの分布が変化する可能性がある場合、モニタリングとアラートを設定し、期待したパフォーマンスが維持されているか継続的に確認することが重要です。Terraform や CloudFormation でインフラをコード管理している環境では、設定変更を IaC に反映し、環境間の一貫性を保つことも忘れずに行いましょう。

## まとめ

今回紹介したアップデートは、Lambda 関数のストレージアクセスパターンをより細かく制御できるようにするもので、特にパフォーマンスチューニングが重要なワークロードにおいて有用です。従来はメモリサイズに応じて自動的に決定されていた動作を、アプリケーションの特性に応じて明示的に選択できるようになったことで、SRE やプラットフォームエンジニアがパフォーマンスとコストのバランスを戦略的に最適化できる余地が広がりました。

追加料金なしで利用できるため、既存の Lambda 関数に対しても気軽に試すことができます。ほぼすべての AWS リージョンで利用可能なため、グローバルに展開しているアプリケーションでも一貫した設定が可能です。ファイルサイズの分布やレイテンシー要件を分析し、自社のワークロードに最適な設定を見つけることで、運用効率の向上につながるでしょう。
