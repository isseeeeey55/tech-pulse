# 直近発表のAWSアップデート情報まとめ — Billing Conductor カスタムレート、SageMaker インスタンス優先度リストほか

## はじめに

今回は、直近で発表された7件のAWSアップデートを紹介します。AWS Billing Conductor のカスタムレート設定、Amazon SageMaker AI のインスタンス優先度リスト、ルートユーザーサインインのリージョナル回復性向上、CloudTrail と Amazon Q Console の統合による自然言語分析、Amazon Connect のシフト入札機能、SageMaker Unified Studio の ODBC 接続対応、そして AWS Glue zero-ETL のテーブル所有権管理まで、多岐にわたる領域でのアップデートが含まれています。

特に注目すべきは、**複雑な課金モデルを柔軟に実装できる Billing Conductor の新機能**と、**SageMaker のジョブ実行効率を大幅に改善するインスタンス優先度リスト**です。これらはそれぞれ、マルチテナント環境やリセラービジネスの運用コスト削減、機械学習パイプラインの開発生産性向上に直結する重要な機能強化となっています。

## 注目アップデート深掘り

### AWS Billing Conductor: カスタムレートと利用段階別料金の直接指定が可能に

AWS Billing Conductor に**カスタムレート**と**利用段階別料金**の設定機能が追加されました。これは、マルチテナント環境やリセラー、グループ企業内課金を運用する組織にとって、大きな生産性向上をもたらすアップデートです。

#### なぜこのアップデートが重要なのか

従来、AWS Billing Conductor で顧客ごとの独自料金体系を実現するには、AWS の公開オンデマンド料金に対して**パーセンテージベースのマークアップ・マークダウン**を設定する方法しかありませんでした。しかし、実際の商業契約では「EC2 インスタンスは 1時間あたり $X、RDS は月額 $Y」といった固定料金や、「月間利用量 100GB まで単価 $0.10/GB、100GB 超は $0.08/GB」のような段階的な料金体系が一般的です。これらを既存のパーセンテージ方式で表現するには、複雑な計算式を組み合わせるか、外部システムで再計算する必要がありました。

今回のアップデートにより、**SKU スコープの料金ルール**で直接カスタム料金と利用段階閾値を指定できるようになり、交渉済みの料金体系をそのまま Billing Conductor に反映できます。これにより、請求計算の透明性が向上し、手動の料金調整作業や計算ミスのリスクが大幅に削減されます。

#### 従来方式との比較

**従来のマークアップ方式**では、例えば「EC2 m5.large を $0.096/時間で提供したい」場合、AWS の公開料金が $0.096 であればマークアップ 0% ですが、料金改定があるたびに再計算とルール更新が必要でした。また、段階的な料金体系を実現するには、複数の条件付きルールを組み合わせる必要があり、管理が煩雑化していました。

**新しいカスタムレート方式**では、以下のような設定が可能になります:

- SKU（例: EC2 m5.large）に対して直接 $0.096/時間 を設定
- 利用段階を定義: 0-100時間は $0.10/時間、100時間超は $0.08/時間
- 複数の SKU に対して異なる料金体系を一括適用

これにより、Pro Forma 請求書に交渉済みの料金がそのまま反映され、顧客への説明が容易になります。

#### 活用シナリオと検証ポイント

マルチテナント SaaS 環境では、顧客ごとに異なる契約条件（エンタープライズ顧客は固定料金、スタートアップは従量課金など）を管理する必要があります。この機能を使えば、Cost Allocation Tags で顧客を識別し、Billing Groups で顧客ごとの料金ルールセットを適用することで、請求処理の自動化が実現できます。

検証時には、以下の点を確認することを推奨します:

1. AWS Billing Conductor コンソールで料金ルール作成時に「カスタムレート」オプションが表示されることを確認
2. 複数の利用段階を設定し、Pro Forma 請求書で各段階の料金が正しく計算されているかを検証
3. 既存のマークアップルールからカスタムレートへの移行パスを設計
4. CloudTrail ログで料金ルール変更の監査証跡を確保

この機能は中国リージョンを除く全商用 AWS リージョンで利用可能です。詳細な設定手順は [AWS Billing Conductor ユーザーガイド](https://docs.aws.amazon.com/billingconductor/) を参照してください。

### Amazon SageMaker AI: インスタンス優先度リストでジョブ開始を高速化

Amazon SageMaker AI のトレーニングおよび処理ジョブに**インスタンス優先度リスト**機能が追加されました。これは、GPU インスタンスの容量制約に悩む機械学習エンジニアにとって、ワークフロー効率を大幅に改善する機能です。

#### 従来の課題と新機能の価値

機械学習のトレーニングジョブでは、特にピーク時間帯に高性能 GPU インスタンス（例: p4d.24xlarge）の容量が確保できず、ジョブが開始待ち状態になることがよくあります。従来は以下のような対応が必要でした:

- ジョブが失敗したら手動で別のインスタンスタイプに変更して再投入
- 複数のインスタンスタイプで並行してジョブを投入し、最初に開始したものを使用
- Lambda や Step Functions で独自のリトライロジックを実装

**インスタンス優先度リスト**を使えば、ジョブ送信時に優先度順に複数のインスタンスタイプ・サイズをリスト指定するだけで、SageMaker が自動的に最初に利用可能な構成を選択してジョブを実行します。これにより、ジョブ開始の待ち時間が短縮され、開発者は複雑なリトライロジックの実装から解放されます。

#### 実装と活用のポイント

この機能は既存の SageMaker API、CLI、SDK、Console でサポートされています。具体的な API 呼び出し方法やパラメータの詳細は [Amazon SageMaker API リファレンス](https://docs.aws.amazon.com/sagemaker/latest/APIReference/) を参照してください。

優先度リストを設計する際のベストプラクティス:

- **最優先**: コストパフォーマンスが最良のインスタンス（例: ml.p4d.24xlarge）
- **次点**: 同等の性能を持つ代替インスタンス（例: ml.p4de.24xlarge）
- **フォールバック**: 性能は劣るが確実に利用可能なインスタンス（例: ml.p3.16xlarge）

また、オンデマンドと SageMaker Flexible Training Plans の容量を同一ジョブ内で混在させることも可能です。例えば、Reserved Capacity を最優先に設定し、容量が不足している場合にのみオンデマンドにフォールバックする構成が考えられます。

#### 定量的な効果測定

ジョブ開始時間の短縮効果を測定するには、以下の指標を記録します:

- ジョブ投入から実行開始までの時間（従来の単一インスタンス指定 vs 優先度リスト）
- ピーク時間帯でのジョブ開始成功率
- リトライロジックの削減による開発工数

特に、営業時間外の定期バッチ処理や、複数チームが同時にトレーニングジョブを実行する環境では、優先度リストによるジョブ開始の確実性向上が大きな価値を持ちます。

この機能は全 AWS リージョンの SageMaker 利用可能エリアで提供されています。

## SRE視点での活用ポイント

### Billing Conductor カスタムレート: 財務可観測性の向上

Billing Conductor のカスタムレート機能は、SRE チームがコスト管理の自動化を推進する上で重要なツールとなります。Terraform で管理している AWS Organizations 環境があれば、Billing Groups と料金ルールを Infrastructure as Code で定義し、顧客追加時の請求設定を自動化できます。また、CloudWatch アラームと組み合わせることで、特定顧客の利用量が段階閾値を超えた際に通知を送り、コスト最適化の提案を自動化することも可能です。

導入時には、既存の請求計算ロジックとの整合性を十分に検証し、移行期間中は並行運用でデータの正確性を確保する必要があります。また、料金ルール変更の監査証跡を CloudTrail で記録し、コンプライアンス要件を満たす運用設計が求められます。

### SageMaker インスタンス優先度リスト: ML パイプラインの信頼性向上

機械学習パイプラインの運用では、ジョブの確実な実行が SLO 達成の鍵となります。インスタンス優先度リストを CI/CD パイプラインに組み込むことで、Step Functions や Airflow で構築されたワークフローの失敗率を削減できます。障害対応のランブックに組み込む場合、「再トレーニングジョブが失敗した場合、どのインスタンスタイプにフォールバックするか」をあらかじめ定義しておくことで、オンコール時の判断を迅速化できます。

一方で、優先度リストに含めるインスタンスタイプは、実際のトレーニング性能を検証した上で選定する必要があります。性能差が大きいインスタンスをリストに含めると、ジョブ完了時間が予測困難になり、下流の処理に影響を与える可能性があります。SageMaker Experiments でインスタンスタイプごとの性能ベンチマークを取得し、許容可能な性能範囲内でリストを構成することが推奨されます。

### CloudTrail と Amazon Q Console の統合: インシデント対応の迅速化

CloudTrail イベントを自然言語で分析できる機能は、インシデント対応時の情報収集を大幅に効率化します。従来は CloudWatch Logs Insights や Athena でクエリを書く必要がありましたが、Amazon Q に「過去24時間に誰がこの VPC のセキュリティグループを変更したか」と質問するだけで回答が得られます。

ただし、この機能はあくまで調査の出発点として活用し、重要な判断には必ず元の CloudTrail イベントを確認するフローを確立すべきです。また、Amazon Q が参照するデータソース（CloudTrail トレイル、CloudWatch ロググループ、イベントデータストア）が適切に設定されているか、定期的に監査する必要があります。

## まとめ

今回紹介したアップデートは、**コスト管理の柔軟性向上**、**機械学習ワークフローの効率化**、**運用の回復性強化**、**データ分析の民主化**といった、多様な運用課題に対応するものでした。

特に Billing Conductor のカスタムレート機能は、マルチテナント環境やリセラービジネスを運用する組織にとって、請求処理の自動化と透明性向上に直結する重要な機能です。また、SageMaker のインスタンス優先度リストは、GPU 容量制約に悩む機械学習チームの生産性を大きく改善します。

ルートユーザーサインインのマルチリージョン対応や CloudTrail の自然言語分析機能は、セキュリティとガバナンスの基盤を強化するものであり、Amazon Connect のシフト入札や SageMaker Unified Studio の ODBC 対応は、エンドユーザー体験の向上に貢献します。

AWS Glue zero-ETL の所有権管理機能は、複雑なデータパイプラインの安全な運用を支援します。これらのアップデートを組み合わせることで、より堅牢で効率的な AWS 運用が実現できるでしょう。各機能の詳細は公式ドキュメントを参照し、自組織の要件に合わせた検証を行うことを推奨します。
