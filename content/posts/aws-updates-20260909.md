# 直近のAWSアップデート情報まとめ（2026年9月）

## はじめに

今回は、直近で発表された8件のAWSアップデートを紹介します。AWS GovCloudリージョンでのサービス拡充、生命科学分野でのワークフロー最適化、セキュリティ機能の強化など、多岐にわたるアップデートが含まれています。特に注目すべきは、AWS TransformとAmazon MWAA ServerlessがAWS GovCloud (US)リージョンで利用可能になったことで、政府機関や規制対象の組織がより広範なAWSサービスを活用できるようになった点です。また、Amazon GuardDutyのカスタム検出ルール、Amazon Bedrock AgentCore MemoryのIngestData API、CloudFrontの動的画像変換機能強化など、運用効率とセキュリティの向上に貢献する機能が多数リリースされています。

本記事では、これらのアップデートの中から特に運用面でのインパクトが大きいものを深掘りし、SREの視点での活用ポイントを解説していきます。

## 注目アップデート深掘り

### Amazon GuardDuty のカスタム検出ルール

Amazon GuardDutyに追加された**Custom Detection Rules**は、CloudTrailの管理イベントに対する脅威検出をより柔軟に制御できる機能です。35個の事前構築されたオプトイン型ルールライブラリが提供され、26種類のユニークな検出タイプをカバーしています。

この機能が重要な理由は、**環境によって脅威の意味が異なる活動に対応できる**点にあります。例えば、AMIの外部共有、VPCフローログの無効化、MFAなしでのサインインといった活動は、本番環境では明確なセキュリティリスクですが、開発環境やサンドボックス環境では正常な運用手順の一部である場合があります。従来のGuardDutyでは、こうした活動を一律に検出するか、まったく検出しないかの二択でしたが、新機能では**環境ごとに必要なルールだけを有効化**できます。

すべてのルールは**10のMITRE ATT&CK®戦術にマッピング**されており、組織のセキュリティフレームワークと整合性を取りやすい設計になっています。例えば、初期アクセス（Initial Access）、持続性（Persistence）、権限昇格（Privilege Escalation）、防御回避（Defense Evasion）といった戦術に対して、どのルールが対応しているかを明確に把握できます。

特筆すべきは**ドライランモード**の存在です。本番環境で有効化する前に、特定のルールがどの程度のアラートを生成するかを評価できるため、誤検知による運用負荷を事前に見積もることができます。これにより、SOC（Security Operations Center）チームは段階的に検出ルールを調整し、環境に最適化された脅威検出体制を構築できます。

また、GuardDutyが**ログの取得、正規化、保存といった重い処理を不要にしている**点も運用上のメリットです。従来の手動ログ監視やサードパーティツールでは、CloudTrailログをS3に保存し、Athenaやサードパーティツールでクエリを実行する必要がありましたが、GuardDutyのカスタムルールはこれらの処理を内部で完結させ、検出結果だけを提供します。

公式ドキュメントでは、各ルールの詳細な検出条件とMITRE ATT&CKマッピングが提供されているため、導入前に組織のセキュリティポリシーとの整合性を確認することを推奨します。

### Amazon Bedrock AgentCore Memory の直接取り込み機能

Amazon Bedrock AgentCore Memoryに追加された**IngestData API**は、エージェントの記憶管理アーキテクチャに大きな変化をもたらす機能です。従来、すべてのコンテンツは短期メモリイベントとして保存される必要がありましたが、新APIにより**長期メモリへの直接取り込み**が可能になりました。

この機能の重要性は、**メモリの運用効率とストレージコストの最適化**にあります。例えば、大量の履歴ログやシステムイベントをエージェントの知識ベースに統合する場合、従来は一度短期メモリに保存してから長期メモリに抽出するという二段階のプロセスが必要でした。これにより短期メモリストレージが肥大化し、管理コストが増大していました。IngestData APIを使用すれば、重要なコンテキストだけを選別して直接長期メモリに送信できるため、**ストレージ効率が大幅に向上**します。

IngestData APIは**2種類のペイロード形式**に対応しています。1つ目は会話ペイロードで、USER/ASSISTANTロールを持つメッセージを含みます。2つ目はJSONペイロードで、行動イベント、アクティビティログ、システムイベントなどの構造化データを扱います。これにより、会話ログとシステムイベントを混在させた複雑なエージェント記憶管理が実現できます。

長期メモリへの抽出処理は**従来のCreateEventと同じパイプライン**で実行されるため、抽出戦略（extraction strategies）の設定や、抽出結果の形式は一貫性が保たれます。抽出ジョブの状態は`ListMemoryExtractionJobs` APIで追跡でき、失敗時の再処理メカニズムも標準的な方法で実装できます。

さらに、**Amazon Kinesis統合**により、メモリ抽出結果をリアルタイムで監視できます。これにより、エージェントが新しい知識を獲得したタイミングをトリガーとして、後続のワークフローを起動するような自動化が可能になります。抽出されたメモリレコードは`ListMemoryRecords`や`RetrieveMemoryRecords` APIで取得でき、エージェントの知識状態を詳細に検証できます。

公式ドキュメントでは、IngestData APIの具体的な使用方法とペイロード形式が詳細に記載されているため、実装前に参照することを推奨します。

### Amazon RDS for MariaDB の量子耐性暗号化対応

Amazon RDS for MariaDBが最新のコミュニティマイナーバージョン（10.6.28、10.11.19、11.4.13、11.8.9、12.3.3）をサポートし、**量子耐性TLS（PQ-TLS）鍵交換**が利用可能になりました。これは量子コンピュータによる将来的な暗号解読リスクに備える重要なセキュリティ強化です。

量子耐性暗号化の重要性は、「Store Now, Decrypt Later（今保存して、後で解読する）」攻撃に対する防御にあります。この攻撃手法では、攻撃者が現在の暗号化通信を記録しておき、将来の量子コンピュータで解読するというシナリオが想定されています。金融機関や医療機関など、長期間のデータ保護が求められる業界では、今から対策を講じる必要があります。

RDS for MariaDBでは、**3つのアップグレード方式**が提供されています。1つ目は**RDS Blue/Greenデプロイメント**で、本番環境と同一構成のGreen環境を作成し、検証後にトラフィックを切り替えることで、ダウンタイムを最小化できます。2つ目は**インプレースアップグレード**で、既存のインスタンスを直接アップグレードします。メンテナンスウィンドウ内で実行されるため、ダウンタイムは発生しますが、手順がシンプルです。3つ目は**スナップショット復元**で、新しいバージョンでインスタンスを新規作成する方法です。

大規模運用環境では、**自動マイナーバージョンアップグレード**と**AWS Organizations Upgrade Rollout Policy**を組み合わせることで、複数アカウント・リージョンにまたがるMariaDBインスタンスを段階的にアップグレードできます。これにより、一部の環境で問題が発生した場合でも、全体への影響を抑制できます。

各マイナーバージョンには、セキュリティパッチ、バグ修正、パフォーマンス改善が含まれています。公式のMariaDBリリースノートで具体的な修正内容を確認し、既存のアプリケーションへの影響を評価することを推奨します。

## SRE視点での活用ポイント

### セキュリティとコンプライアンスの自動化

GuardDutyのカスタム検出ルールは、SREチームがセキュリティ運用を効率化する強力なツールです。**環境別のセキュリティポリシーをコードとして管理**する運用が可能になります。例えば、TerraformでGuardDutyの検出ルール設定を管理している場合、開発環境では`ami_external_sharing`ルールを無効化し、本番環境でのみ有効化するといった制御が宣言的に記述できます。

ドライランモードを活用すれば、**新しいルールの影響範囲を本番環境に影響を与えずに評価**できます。CloudWatchメトリクスとアラームを組み合わせて、ドライランモードで検出された脅威の件数を監視し、一定期間の統計を取得してから本番有効化を判断する、といったデータドリブンな意思決定プロセスが構築できます。

また、GuardDutyの検出結果をEventBridgeルールでキャッチし、Lambda関数経由でインシデント管理システム（PagerDuty、Opsgenie等）に自動連携するパイプラインを構築することで、**脅威検出から対応までの自動化**が実現できます。MITRE ATT&CK戦術にマッピングされているため、インシデント対応のランブックも戦術別に整理しやすくなります。

### エージェントシステムの知識管理最適化

Bedrock AgentCore MemoryのIngestData APIは、エージェントベースの自動化システムを運用する際の**メモリ管理戦略を大きく改善**します。例えば、障害対応エージェントを構築する場合、過去の障害ログやRunbook実行履歴を長期メモリに直接取り込むことで、エージェントが過去の対応パターンを学習し、類似障害への対応精度を向上させることができます。

短期メモリと長期メモリを独立して運用できるため、**リアルタイムの対話セッション（短期）と組織の知識ベース（長期）を分離**して管理できます。これにより、セッション終了後も重要な知見だけを長期メモリに保存し、エージェントの知識を段階的に蓄積する運用が可能になります。

Kinesis統合により、メモリ抽出の成功/失敗をリアルタイムで監視できるため、**メモリ更新の品質管理**を自動化できます。抽出失敗が一定件数を超えた場合にアラートを発火させ、メモリ抽出戦略の見直しを促すといった運用が考えられます。

### データベースアップグレードのリスク管理

RDS for MariaDBのアップグレード運用では、**Blue/Greenデプロイメントを活用したリスク最小化**が鍵となります。本番環境でBlue環境を稼働させながら、新バージョンのGreen環境で性能テストと結合テストを実施し、問題がなければ切り替える、というフローを標準化できます。

自動マイナーバージョンアップグレードを有効化する場合は、**メンテナンスウィンドウの設定が重要**です。トラフィックが最小となる時間帯を選び、CloudWatchアラームでRDSのCPU使用率やレプリケーション遅延を監視しながらアップグレードを実施することで、ビジネス影響を最小化できます。

AWS Organizations Upgrade Rollout Policyを使用すれば、**複数アカウントでの段階的ロールアウト**が可能です。例えば、開発アカウント → ステージングアカウント → 本番アカウントの順にアップグレードを展開し、各段階で問題がないことを確認してから次に進む、といったCanaryリリース方式を採用できます。

量子耐性暗号化については、現時点で即座の対応が必要なケースは限定的ですが、**規制要件として求められる前に対応しておく**ことで、将来的なコンプライアンス対応コストを削減できます。特に金融機関や医療機関では、早期の対応検討を推奨します。

## まとまとめ

今回紹介した8件のアップデートは、**AWS GovCloudでのサービス拡充**、**生命科学・AI分野での運用効率化**、**セキュリティ機能の強化**という3つの大きなトレンドを示しています。

AWS TransformとMWAA ServerlessがGovCloudリージョンで利用可能になったことで、政府機関や規制対象組織が最新のクラウド技術を活用できる範囲が広がりました。特にサーバーレスオプションの提供は、インフラ管理の運用負荷削減とコスト最適化の両面で大きなメリットをもたらします。

HealthOmicsのリソースフォールバック機能とBedrock AgentCore MemoryのIngestData APIは、それぞれ生命科学とAIエージェント分野での運用効率を大幅に向上させる機能です。どちらも**リソース管理の自動化と柔軟性の向上**を実現しており、SREチームの運用負荷を軽減します。

GuardDutyのカスタム検出ルールとRDS for MariaDBの量子耐性暗号化は、**将来のセキュリティリスクへの備え**という点で重要です。特にGuardDutyの環境別ルール設定は、開発速度とセキュリティのバランスを取る上で非常に有用です。

CloudFrontの画像最適化機能は、グローバル配信の品質とコストの両面で改善をもたらします。デバイス分類とClient Hintsの組み合わせにより、従来最適化されていなかった約30%のトラフィックも最適化対象に含まれるようになり、ユーザー体験の向上とインフラコストの削減が期待できます。

これらのアップデートを活用することで、セキュリティ、パフォーマンス、運用効率の各側面で AWS 環境を継続的に改善していくことができるでしょう。
